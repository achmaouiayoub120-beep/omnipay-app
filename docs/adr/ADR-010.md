# ADR-010 — Observabilité pilotée par les SLO et alertes de budget d'erreur

| Champ | Valeur |
|---|---|
| **Titre** | Observabilité pilotée par les SLO et alertes de consommation de budget d'erreur |
| **Statut** | **Accepté** |
| **Date** | 2026-11-19 |
| **Porteur** | P5 — Fiabilité, observabilité et retour d'expérience |
| **Réviseurs** | P1 (Lead technique), P2 (Développement), P4 (CI/CD) |

---

## Contexte

La plateforme OmniPay Zero-Trust est une application FinTech composée de 3 microservices Spring Boot (Auth, Transaction, Notification) déployés sur un cluster K3s via une approche GitOps (ArgoCD).

En tant que mini-banque en ligne soumise au principe Zero-Trust, les exigences de fiabilité sont élevées :
- Les **transactions financières** (virements, consultation de solde) ne tolèrent qu'un taux d'erreur minimal.
- Le **service d'authentification** est un point de passage obligatoire ; sa latence impacte l'ensemble de la chaîne.
- Le **service de notifications** doit informer l'utilisateur en temps quasi-réel.

Sans une stratégie d'observabilité structurée, l'équipe risque de :
1. Réagir aux incidents *a posteriori* plutôt que de les anticiper.
2. Alerter sur des seuils statiques déconnectés de l'impact utilisateur réel (fatigue d'alerte).
3. Ne pas pouvoir quantifier objectivement la fiabilité de la plateforme.
4. Manquer de données pour arbitrer entre vélocité de déploiement et stabilité (budget d'erreur).

---

## Décision

Adopter une **observabilité pilotée par les SLO (Service Level Objectives)** avec la stack suivante :

| Composant | Outil | Rôle |
|---|---|---|
| Collecte de métriques | **Prometheus** (kube-prometheus-stack) | Scraping, stockage TSDB, évaluation de règles |
| Visualisation | **Grafana** | Dashboards, exploration de métriques |
| Alerting | **Alertmanager** | Routage, déduplication et notification |
| Instrumentation | **Micrometer + Spring Boot Actuator** | Métriques JVM et HTTP sur `/actuator/prometheus` |
| Infrastructure | **node-exporter + kube-state-metrics** | Métriques nœuds K3s et objets Kubernetes |
| Gestion CRD | **Prometheus Operator** | ServiceMonitor, PrometheusRule |

### Principes directeurs

1. **SLO-driven alerting** : Les alertes sont déclenchées par la consommation du budget d'erreur, pas par des seuils statiques arbitraires.
2. **Golden Signals** : Chaque microservice est surveillé selon les 4 signaux de Google SRE (Latence, Trafic, Erreurs, Saturation).
3. **Approche GitOps** : Tous les manifestes de monitoring (ServiceMonitor, PrometheusRule, values Helm) sont versionnés dans `omnipay-gitops/platform/monitoring/`.
4. **Scraping déclaratif** : Les `ServiceMonitor` CRD découvrent automatiquement les microservices via les labels Kubernetes (`monitored: "true"`).

### SLO définis

| Service | SLO | Objectif | Budget d'erreur (30j) |
|---|---|---|---|
| Auth Service | Disponibilité | 99.9 % | 43.2 min |
| Transaction Service | Disponibilité | 99.95 % | 21.6 min |
| Transaction Service | Taux d'échec virement | < 0.01 % | — |
| Notification Service | Disponibilité | 99.5 % | 3.6 h |

## Alternatives étudiées

| Alternative | Raison du rejet |
|---|---|
| **ELK Stack seul** (Elasticsearch + Kibana) | Ne couvre pas les métriques temps-réel ni les SLO quantitatifs (latence P95/P99). Complémentaire, pas suffisant. |
| **APM SaaS** (Datadog, New Relic) | Coût prohibitif pour un projet académique. Dépendance externe incompatible avec la philosophie Zero-Trust et l'approche offline/on-premise. |
| **Seuils statiques uniquement** (CPU > 80 %, RAM > 90 %) | Faux positifs fréquents. Déconnecté de l'impact utilisateur. Un pod peut utiliser 90 % CPU en répondant correctement. |

---

## Conséquences

### Positives
1. **Alignement business-technique** : Les SLO traduisent l'expérience utilisateur en métriques mesurables.
2. **Réduction du bruit d'alerting** : Le burn-rate alerting élimine les faux positifs.
3. **Arbitrage vélocité/stabilité** : Budget d'erreur positif → déploiements rapides. Budget épuisé → gel et fiabilisation.
4. **Stack 100 % open-source** : Pas de coût de licence, intégration native K8s et Spring Boot.
5. **Base pour le Canary Release** : Prometheus fournit les métriques d'analyse pour Argo Rollouts (P4 — Démo 1).
6. **Base pour le Game Day** : Les dashboards et alertes seront validés par injection de chaos (Chaos Mesh — Démo 5).

### Négatives
1. **Courbe d'apprentissage PromQL** : Requiert un investissement pour écrire des requêtes précises.
2. **Consommation de ressources** : Prometheus consomme de la mémoire proportionnellement au nombre de séries temporelles. Dimensionnement soigné requis sur K3s.
3. **Rétention limitée** : 7 jours avec 10 Gi de stockage (acceptable pour le projet académique).
4. **Mot de passe Grafana** : Présent dans `values-prometheus.yaml`. Migration vers SealedSecrets planifiée en Semaine 2.

---

## Sécurité

- Lien direct avec le Threat Model STRIDE (voir `docs/security/threat-model-stride.md`) :
  - **STRIDE-D2** : Les limites de ressources définies dans les values Helm préviennent les DoS par saturation.
  - **STRIDE-R1** : La journalisation des métriques de transaction dans Prometheus assure la traçabilité (non-répudiation).
- Le mot de passe Grafana est un secret de simulation académique documenté. En production, il serait géré par Vault (ADR-006).
