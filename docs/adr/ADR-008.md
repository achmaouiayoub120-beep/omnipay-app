# ADR-008 — Stratégie de gestion de branches, Conventional Commits et détection préventive des secrets

## Statut
**Accepté**

## Contexte
Dans un projet bancaire Zero-Trust à cinq intervenants simultanés, le risque de collision de code, de pollution de l'historique Git et surtout d'exposition accidentelle de données d'authentification ou de jetons privés dans le dépôt public/privé est critique.
Un secret commité dans Git, même supprimé dans un commit ultérieur, reste consultable dans l'historique et doit être considéré comme irrémédiablement compromis.

L'équipe a besoin d'une convention unifiée pour :
1. Structurer le flux de branches pour supporter le Continuous Integration et le Continuous Delivery (GitOps).
2. Standardiser les messages de commit pour faciliter la génération automatique de changelogs et le suivi sémantique.
3. Bloquer systématiquement toute tentative de commit ou de push contenant des clés API, certificats ou mots de passe (approche Shift-Left).

## Décision
1. **Modèle de branches** :
   - Branche principale protégée : `main` (miroir de la production).
   - Branche d'intégration continue : `develop`.
   - Branches de travail éphémères : `feature/*`, `fix/*`, `security/*`, `docs/*`.
   - Interdiction formelle du push direct et du force-push (`git push --force`) sur `main` et `develop`.
   - Toute fusion requiert une Pull Request avec relecture croisée par au moins un membre de l'équipe (règle des binômes).

2. **Standard Conventional Commits** :
   - Adoption du format `<type>(<scope>): <description>` avec types stricts (`feat`, `fix`, `ci`, `security`, `docs`, `test`, `refactor`, `infra`).

3. **Détection des secrets Shift-Left avec Gitleaks** :
   - Analyse locale préventive via pre-commit hook ou script avant de pousser.
   - Stage obligatoire bloquant dans le pipeline Jenkins (`gitleaks git .`).
   - Configuration centralisée via `.gitleaks.toml`.

## Alternatives étudiées
1. **Trunk-Based Development pur (push direct sur main)** :
   - Rejeté : trop risqué dans une équipe académique avec des profils techniques hétérogènes ; absence de filet de sécurité avant déploiement GitOps.
2. **Gitflow complet avec branches release/ et hotfix/ lourdes** :
   - Rejeté : trop complexe pour un cycle de 4 semaines avec déploiements continus fréquents (canary, dev/recette/prod).
3. **TruffleHog ou GitGuardian SaaS pour la détection de secrets** :
   - Rejetés pour la baseline : GitGuardian dépend d'une clé cloud externe ; Gitleaks est autonome, rapide, sans dépendance externe et s'intègre nativement en CLI locale ou dans un conteneur Jenkins.

## Conséquences
- **Avantages** :
  - Historique Git lisible, auditable et aligné avec les exigences d'un audit de conformité bancaire.
  - Éradication proactive des fuites de credentials avant même qu'ils n'atteignent le serveur Git distant.
  - Revue de code obligatoire renforçant l'oral croisé et la polyvalence de l'équipe.
- **Inconvénients / Défis** :
  - Nécessite une discipline d'équipe stricte (pas de commits « quick fix » bâclés).
  - Gestion des faux positifs éventuels via `.gitleaks.toml`.

## Sécurité
- Ce choix matérialise le principe de défense en profondeur : vérification chez le développeur (pre-commit), validation à la porte d'entrée (Pull Request review), et vérification automatisée par la CI (Jenkins stage Gitleaks).

## Justification
Cette stratégie formalise une hygiène logicielle de niveau professionnel, garantit la reproductibilité des revues de code et protège le patrimoine cryptographique d'OmniPay Zero-Trust dès le Jour 1.
