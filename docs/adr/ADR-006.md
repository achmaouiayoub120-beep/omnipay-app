# ADR-006 : Gestion des secrets CI/CD, identités machines et intégration HashiCorp Vault

## Statut
**Accepté** (Semaine 2 — Rôle P1 & P3)

## Contexte
La plateforme bancaire simulée **OmniPay Zero-Trust** manipule plusieurs types de secrets critiques :
1. **Secrets de pipeline CI/CD :** Tokens d'accès GitHub, credentials du registre Harbor, clés privées de signature Cosign, tokens d'analyse SonarQube et webhooks de notification.
2. **Secrets applicatifs :** Mots de passe de base de données PostgreSQL, clés de signature JWT, credentials SMTP.
3. **Secrets d'infrastructure :** Clés SSH, kubeconfig, certificats TLS.

En conformité avec les principes Zero-Trust et les exigences académiques du projet :
* **Zéro secret dans Git :** Aucun mot de passe, token ou clé privée ne doit jamais être versionné dans `omnipay-app` ou `omnipay-gitops`.
* **Identités éphémères et moindres privilèges :** Les identifiants statiques partagés constituent un vecteur d'attaque majeur.
* **Séparation stricte des responsabilités :** Jenkins ne doit détenir que les identifiants minimaux requis pour construire et signer les artefacts, sans accès direct en écriture au cluster de production.

## Décision
Nous adoptons une architecture de gestion des secrets à deux niveaux :

### 1. Niveau CI/CD (Jenkins JCasC & Kubernetes Secrets)
* **Configuration as Code :** Les credentials Jenkins sont déclarés via Jenkins Configuration as Code (`ci/jenkins-casc.yaml`) et alimentés par des variables d'environnement injectées au runtime.
* **Isolation DooD / Pods agents :** La clé de signature Cosign (`cosign.key`) est stockée dans un Kubernetes Secret dans le namespace `jenkins` ou injectée de façon éphémère lors du stage de signature, sans persistance sur le disque de l'agent.
* **Write-back GitOps restreint :** Jenkins utilise un token GitHub scoped (`repo` write sur `omnipay-gitops` uniquement) pour mettre à jour les tags Kustomize sans droits d'administration.

### 2. Niveau Plateforme & Applications (HashiCorp Vault)
* **Vault en mode High-Availability ou Dev/Audit K3s :** Déployé dans le namespace `vault` sur K3s.
* **Moteur de secrets dynamiques PostgreSQL :** Vault génère des utilisateurs PostgreSQL éphémères avec un TTL court (ex: 1 heure) pour les microservices (`auth-service` et `transaction-service`).
* **Vault Agent / CSI Driver :** Les identifiants sont montés sous forme de fichiers mémoire ou injectés via variables d'environnement sans que le mot de passe n'existe dans un fichier statique.

## Alternatives analysées et rejetées
* **Hardcoded / Git-crypt :** Rejeté car viole le principe fondamental Zero-Trust et expose les clés au risque d'historique Git compromis.
* **Kubernetes Secrets natifs statiques seuls :** Rejeté car les secrets Kubernetes de base ne sont que du Base64 sans rotation automatique ni audit d'accès dynamique.
* **Sealed Secrets seul :** Utile pour le chiffrement asymétrique dans GitOps, mais insuffisant pour la génération dynamique de credentials bancaires (pas de rotation active côté base de données).

## Conséquences et garanties
* **Traçabilité :** Tout accès à un secret fait l'objet d'un log d'audit.
* **Résilience (Démo 4 du jury) :** La révocation d'un mot de passe PostgreSQL dans Vault n'interrompt pas le service car les microservices renouvellent dynamiquement leur pool de connexions.
* **Hygiène CI/CD :** Gitleaks valide en amont qu'aucun commit ne contient d'artefact sensible.
