# ADR-011 : Gestion dynamique des secrets au runtime (HashiCorp Vault & ESO) et détection d'intrusions eBPF/Falco

| Champ | Valeur |
| :--- | :--- |
| **Porteur** | P3 - Plateforme, IaC, réseau et conformité |
| **Statut** | **Accepté** |
| **Date** | Semaine 3 |

## Contexte et menaces (STRIDE)

Les ADR précédents ont posé l'isolation réseau (ADR-009) et l'admission d'images signées. Reste le
**runtime** : que se passe-t-il quand un conteneur est compromis malgré tout ?

| Menace STRIDE | Scénario | Sans cette décision |
| :--- | :--- | :--- |
| **E**levation of privilege / déplacement latéral | Un attaquant exécutant du code dans un pod lit des variables d'environnement ou fichiers contenant des mots de passe statiques, puis réutilise ces identifiants ailleurs | Mot de passe DB unique, durable, présent dans Git ou dans un Secret en base64 |
| **I**nformation disclosure | Lecture du token ServiceAccount, de `/etc/shadow` ou d'un secret monté | Aucune détection |
| **T**ampering / **R**epudiation | Lancement d'un shell ou d'un binaire parasite (`nc`, `nmap`, `curl`) dans un pod qui n'en exécute jamais | Aucune trace exploitable |

Cette décision complète l'ADR-006 (secrets CI/CD et identités machines) côté runtime applicatif.

Exigences PCI-DSS concernées :
- **3.5 et 3.6** : protection et gestion du cycle de vie des clés et secrets ; aucun secret en clair dans
  les dépôts de code source ; séparation des fonctions (qui stocke, qui consomme).
- **10.2 et 10.5** : journalisation des accès privilégiés et détection en temps réel, journaux protégés
  contre la modification.

## Décision

1. **HashiCorp Vault** (namespace `vault`, mode standalone, stockage sur PVC `local-path`, UI en
   NodePort 30006) est le magasin central des secrets : moteur KV v2 `secret/`, authentification
   Kubernetes, politique `omnipay-app-policy` en **lecture seule** sur `secret/data/omnipay/*`.
2. **External Secrets Operator** découple Vault des applications : un `ClusterSecretStore`
   (`vault-backend`) et des `ExternalSecret` produisent les Secrets Kubernetes natifs
   (`omnipay-postgres-credentials`, `omnipay-jwt-secret`) dans `omnipay-dev|recette|prod`, avec
   `refreshInterval: 1h`. **Seul ESO parle à Vault** : le rôle Vault `omnipay-role` est lié à son
   ServiceAccount (`external-secrets/eso-vault-auth`), les pods applicatifs n'ont aucun accès à Vault.
3. **Falco** (DaemonSet, sonde modern eBPF, namespace `falco`) surveille les appels système du noyau avec
   3 règles bancaires sur les namespaces `omnipay-*` : shell dans un pod (CRITICAL), lecture de
   `/etc/shadow`, `/root/.ssh` ou du token ServiceAccount (CRITICAL), outils réseau
   `nmap/nc/tcpdump/curl` (WARNING). Falcosidekick relaie les alertes vers Alertmanager.
4. **Aucun secret dans Git.** Les valeurs initiales (mot de passe DB, clé JWT) sont générées
   aléatoirement dans le pod Vault par `init-vault.sh` et n'apparaissent dans aucun fichier. Les clés
   d'unseal et le root token sont écrits dans le Secret `vault/vault-unseal-keys`, jamais sur disque.

## Alternatives écartées

| Option | Raison du rejet |
| :--- | :--- |
| **Sealed Secrets (Bitnami)** | Chiffrement asymétrique des secrets *dans Git* : le secret chiffré reste statique, sans rotation dynamique ni révocation instantanée, et la clé privée du contrôleur devient un point unique |
| **Secrets Kubernetes natifs seuls** | Base64 (pas du chiffrement) dans etcd, contrôle d'accès fin limité au RBAC, pas d'audit des lectures, secret souvent présent dans Git |
| **Vault Agent Injector** | Sidecar par pod (RAM, surface d'attaque) alors qu'ESO fournit des Secrets natifs sans modifier les Pods |
| **Audit via les logs d'audit Kubernetes seuls** | Voit les appels API, pas les appels système dans le conteneur (shell, lecture de fichier) |

## Conséquences

**Positives**
- Plus aucun secret statique dans Git ; un secret se change dans Vault et se propage sans commit.
- Un pod compromis ne peut pas atteindre Vault ; la politique est en lecture seule et bornée à `omnipay/*`.
- Détection en temps réel des comportements impossibles pour un microservice sain (shell, lecture du
  token), avec contexte pod/namespace/utilisateur/commande, démontrable en soutenance (Démo 4).
- Alignement PCI-DSS 3.5, 3.6, 10.2.

**Négatives, limites et mitigations**
- **Unseal manuel au redémarrage de Vault** : après un redémarrage du pod, relancer `init-vault.sh`
  (idempotent) re-déverrouille. *Évolution :* auto-unseal via un KMS (hors périmètre du laboratoire).
- **Clés d'unseal dans un Secret Kubernetes** : acceptable en laboratoire, insuffisant en production
  (PCI-DSS 3.6 : séparation des détenteurs de clés). *Mitigation :* les copier dans un coffre
  hors cluster puis supprimer le Secret ; documenté à la fin de `init-vault.sh`.
- **Vault en HTTP interne** (`tls_disable`). *Mitigation :* trafic limité au cluster ; TLS via cert-manager
  prévu ensuite.
- **Falco détecte, il ne bloque pas.** Une règle ne tue pas le processus. *Mitigation :* alertes vers
  Alertmanager ; une réponse automatique (Falco Talon) peut être ajoutée plus tard.
- **Journal « infalsifiable » (PCI-DSS 10.5)** : Falco émet les alertes sur stdout/syslog ; l'intégrité du
  journal dépend de leur collecte vers un stockage append-only (Loki/stack de P5), non couvert ici.
- **Rotation côté application** : `refreshInterval: 1h` met à jour le Secret Kubernetes, mais une
  variable d'environnement n'est relue qu'au redémarrage du conteneur ; monter le Secret en volume ou
  faire un rolling restart.
- **Falco exige un namespace `privileged`** (sonde eBPF). *Mitigation :* namespace dédié sans workload
  applicatif, capabilities réduites (`leastPrivileged`).
- **Dépendance au noyau** : la sonde modern eBPF requiert un noyau Linux ≥ 5.8 (BTF).
