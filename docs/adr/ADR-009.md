# ADR-009 : Politique de micro-segmentation réseau Zero-Trust (NetworkPolicies deny-all)

| Champ | Valeur |
| :--- | :--- |
| **Porteur** | P3 - Plateforme, IaC, réseau et conformité |
| **Statut** | **Accepté** |
| **Date** | Semaine 2 |

## Contexte

Par défaut, Kubernetes autorise tous les pods à communiquer entre eux sur le réseau du cluster. Si un
microservice est compromis, par exemple par une faille d'exécution de code à distance (RCE) dans
`notification-service`, l'attaquant peut atteindre directement PostgreSQL, scanner le réseau interne et
exfiltrer des données vers Internet : c'est le **déplacement latéral**.

Cette posture est incompatible avec la doctrine Zero-Trust du projet et avec les exigences d'un système
de paiement (PCI-DSS, exigences 1.2 et 1.3 : segmentation du réseau et restriction du trafic vers
l'environnement de données de titulaires de cartes).

## Décision

Dans chaque namespace applicatif (`omnipay-dev`, `omnipay-recette`, `omnipay-prod`) :

1. Une NetworkPolicy **`default-deny-all`** (`podSelector: {}`, `policyTypes: [Ingress, Egress]`) bloque tout
   le trafic entrant et sortant.
2. Seuls les flux ci-dessous sont ouverts, port par port et pod à pod (sélection par
   `app.kubernetes.io/name`). Un flux n'existe que si l'egress de la source **et** l'ingress de la
   destination l'autorisent.

| Source | Destination | Port | Justification |
| :--- | :--- | :--- | :--- |
| Ingress controller NGINX (`ingress-nginx`) | `auth` | 8081 | Entrée HTTPS des clients |
| Ingress controller NGINX (`ingress-nginx`) | `transaction` | 8082 | Entrée HTTPS des clients |
| `auth` | `postgresql` | 5432 | Persistance des utilisateurs |
| `transaction` | `postgresql` | 5432 | Persistance des transactions |
| `transaction` | `notification` | 8083 | Émission d'événements |
| Prometheus (`monitoring`) | `auth`, `transaction`, `notification` | 8081, 8082, 8083 | Scrape `/actuator/prometheus` |
| Tous les pods | `kube-system/kube-dns` | 53 UDP/TCP | Résolution DNS |

Tout autre flux est refusé, notamment `notification` vers `postgresql` et toute sortie directe vers
Internet.

Les manifestes sont dans `infra/network-policies/`. Le script `infra/scripts/test-network-policies.sh`
prouve le comportement : `transaction` atteint `postgresql:5432`, `notification` est bloqué, la sortie
Internet est bloquée.

## Alternatives écartées

| Option | Raison du rejet |
| :--- | :--- |
| Aucune politique (réseau plat) | Déplacement latéral libre après compromission |
| Maillage de services (Istio, Linkerd) | Trop lourd pour une machine étudiante ; mTLS pertinent plus tard, les NetworkPolicies L3/L4 couvrent le besoin immédiat |
| NetworkPolicies Cilium / Calico (L7, FQDN) | Nécessite de remplacer le CNI embarqué de K3s ; hors périmètre |

## Conséquences

**Positives**
- Confinement : un pod compromis ne peut atteindre que ce que son rôle exige.
- Le service de notification n'a aucun accès à la base de données.
- Politiques déclaratives, versionnées, revues par PR et auditées (`audit-iac.sh`).
- Alignement avec PCI-DSS (segmentation, moindre privilège réseau).

**Négatives et mitigations**
- Tout nouveau flux doit être déclaré. *Mitigation :* matrice ci-dessus + revue de PR.
- Le chart Helm de P2 doit conserver les labels `app.kubernetes.io/name`. *Mitigation :* labels générés par `omnipay.selectorLabels`.
- PostgreSQL doit porter `app.kubernetes.io/name: postgresql`. *Mitigation :* à vérifier lors de son déploiement.
- **Journalisation des paquets rejetés :** les NetworkPolicies Kubernetes ne journalisent pas nativement les paquets refusés. Avec le contrôleur embarqué de K3s (kube-router), les rejets sont visibles dans les compteurs iptables/ipset du noeud, mais il n'existe pas de journal d'audit dédié. Un journal exploitable demande un CNI à observabilité réseau (Cilium Hubble) : à évaluer, non couvert par cette ADR.
- Le contrôleur de NetworkPolicy de K3s doit rester actif (pas de `--disable-network-policy`). *Mitigation :* `test-network-policies.sh` échoue si la segmentation n'est pas appliquée.
