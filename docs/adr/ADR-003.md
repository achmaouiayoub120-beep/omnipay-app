# ADR-003 — Choix du moteur d'intégration continue : Jenkins avec JCasC et agents dynamiques

## Statut
**Accepté**

## Contexte
Le projet OmniPay Zero-Trust simule une plateforme financière soumise à des exigences strictes de gouvernance, de traçabilité, de sécurité logicielle et d'autonomie d'infrastructure.
Nous devons orchestrer une chaîne d'intégration continue (CI) capable de :
1. Cloner les sources et auditer préventivement l'absence de fuite d'identifiants (Gitleaks).
2. Compiler les microservices Java / Spring Boot et exécuter les suites de tests unitaires et d'intégration.
3. Exécuter les contrôles de qualité et de sécurité (SonarQube, OWASP Dependency-Check, Trivy).
4. Construire les conteneurs Docker, générer le SBOM (Syft) et signer cryptographiquement les artefacts (Cosign).
5. Être entièrement reproductible sans configuration manuelle via l'interface graphique (Configuration as Code).
6. S'exécuter dans un environnement maîtrisé sur nos propres machines ou serveurs sans dépendre d'un service SaaS tiers payant.

## Décision
Nous retenons **Jenkins LTS configuré par Jenkins Configuration as Code (JCasC)** avec un pipeline déclaratif (`Jenkinsfile`) et l'exécution des builds sur des agents dynamiques (conteneurs Docker en local, puis pods éphémères sur K3s).

Pour garantir la reproductibilité :
- L'ensemble de la configuration du contrôleur Jenkins (sécurité, plugins, credentials, jobs) est décrit dans `ci/jenkins-casc.yaml`.
- Le contrôleur n'exécute aucun job directement (nombre d'exécuteurs locaux = 0 ou minimal).
- Les étapes de build et de scan sont isolées dans des conteneurs ou des pods dédiés.

## Alternatives étudiées
1. **GitHub Actions (SaaS)** :
   - *Avantages* : Intégration native à GitHub, syntaxe YAML fluide, maintenance nulle de l'infrastructure CI.
   - *Inconvénients* : Dépendance envers une plateforme externe (hors du périmètre du cours ESTC axé sur Jenkins), consommation de quotas d'heures de build, opacité relative sur l'environnement d'exécution par rapport aux exigences d'un cas bancaire Zero-Trust auto-hébergé.
2. **GitLab CI** :
   - *Avantages* : Très puissant, runners efficaces, excellent écosystème DevSecOps intégré.
   - *Inconvénients* : Nécessiterait de migrer l'ensemble des dépôts sur une instance GitLab ou GitLab.com, en conflit avec l'architecture GitHub retenue pour ce projet.
3. **Jenkins avec configuration manuelle par interface graphique (GUI)** :
   - *Rejeté catégoriquement* : Non reproductible, non versionné, sujet à des dérives de configuration (snowflake server).

## Conséquences
- **Avantages** :
  - Alignement direct avec le programme pédagogique DevOps / DevSecOps.
  - Reproductibilité intégrale : destruction et reconstruction de l'instance CI en une commande (`docker compose up -d`).
  - Maîtrise totale des secrets injectés et de l'environnement d'exécution.
  - Évolutivité vers des agents Kubernetes dynamiques sur K3s dès la Semaine 2.
- **Inconvénients / Défis** :
  - Consommation mémoire non négligeable pour le contrôleur Jenkins (JVM, ~1 à 2 Go de RAM).
  - Nécessité de verrouiller rigoureusement les versions des plugins Jenkins pour éviter les régressions.

## Sécurité
- Le contrôleur Jenkins applique le principe de moindre privilège : sécurité globale activée (`authorizationStrategy`), interdiction d'accès anonyme.
- Aucun mot de passe ni clé API n'est stocké en dur dans le fichier `jenkins-casc.yaml` : utilisation exclusive des variables d'environnement pour l'initialisation des secrets.
- Isolation des builds : l'exécution des tests et outils de scan sur des agents isolés évite toute compromission du contrôleur en cas de dépendance vulnérable.

## Justification
Jenkins avec JCasC offre le compromis optimal entre respect des exigences académiques, contrôle architectural total et conformité aux standards professionnels de l'Infrastructure as Code appliquée à la CI/CD.
